# `fixtures/` — two consumer apps

Roadmap P3-6. Two ordinary apps that depend on Prism the way someone outside this repository does,
built against **packed and tagged artefacts** and never against the workspace. They are the release
rehearsal's acceptance check: if a subpath, a font, a license or a `workspace:` specifier is wrong,
these builds fail before a registry ever sees the package.

| | `swiftui-app/` | `vite-app/` |
|---|---|---|
| Depends on | the SwiftPM package, by path or at a tag | the two npm tarballs `pnpm pack` writes |
| Built by | `pnpm fixtures:apple` (`tools/release/fixture-apple.ts`) | `pnpm fixtures:web` (`tools/release/fixture-web.ts`) |
| Proves | `xcodebuild` builds an iOS app against `DSComponents`; SwiftPM resolves the tag | `vite build` resolves every subpath the skill names, and the built page applies Prism |

Neither app is a workspace package: `pnpm-workspace.yaml` matches one level under `web/apps/`, and
these live here, so `pnpm install` never links them. That is the point — a linked package resolves
subpaths against the source tree, and a file the tarball leaves out would still resolve.

## The Vite app

```
pnpm -r build             # the packages' dist/, which their export maps point at
pnpm fixtures:web         # pack, install, vite build, smoke

# With arguments, call the script itself: `pnpm run` would hand --version and friends to pnpm.
node tools/release/fixture-web.ts --tarballs <dir>   # tarballs release:pack already wrote
node tools/release/fixture-web.ts --work <dir>       # build there, not in a temporary directory
```

The app is copied into a work directory, the two `file:` specifiers are pointed at the tarballs, and
`npm install` resolves the peers and the runtime dependencies from the registry — a consumer's
install, not pnpm's workspace resolution. `src/app.css` is the stylesheet block `agent/SKILL.md` gives
a consuming app, minus Tailwind; `src/main.jsx` is `<Theme>` at the root with the brand table handed
over once (ADR-0020 §6), and one of Surface, Text, Button and Card.

`smoke.mjs` then serves `dist/`, opens it in Chromium and asks the page three questions a broken
package would answer differently: a `--ds-*` variable has a value **and** the element painted it; the
brand's own face is ready and came from this origin rather than the network (ADR-0021 §11); pressing
the app's own Button flips `<Theme>`'s colour scheme, `<html>` gets the attribute the published
runtime spells, and the page repaints to the other scheme's token (ADR-0019 §4).

That last one is the one that is easy to fake, so it is worth knowing how it is asked. `<Surface>`
crossfades its colours, so the attribute flips a frame before the colour arrives and a probe taken
there reports the scheme that is *leaving*; `smoke.mjs` waits for `window.prismFixture.settled()`
first. And a colour is compared as the sRGB bytes it paints, never as the string Chromium serializes
it to — the same colour comes back as `oklch(…)` when it is painted and as `oklab(…)` while it is
being interpolated, so a string comparison reads a re-serialization as a repaint that never
happened. `src/main.jsx` does both, which is why this file still holds no browser code.

## The SwiftUI app

```
pnpm fixtures:apple       # the package at this checkout, by path

node tools/release/fixture-apple.ts --package tag --repo <path|url> --version 0.2.0   # as a consumer gets it
```

`PrismFixture/` holds the sources; the `.xcodeproj` is generated by the build script and is not
committed, because the one thing that differs between a rehearsal and a real consumer is the package
reference — a local path, or a git repository resolved at an exact tag. A `file://` URL to a scratch
clone is a repository like any other to SwiftPM, so rehearsing a tag needs no network and no push.

The app wraps its scene in `DSTheme(brand: .prism)`, reads everything through the environment's
`DSTokenSet`, and renders Surface, Text, Button and Card. It links `DSComponents` only; `DSCore`,
`DSTokens` and `DSIcons` come with it, and the built `.app` carries `Prism_DSTokens.bundle` with the
compiled colour catalog and the brand's font files.

## When one of them fails

A fixture failure is a consumer's failure, not a fixture bug. Read it as:

* a missing subpath or file → the package's `exports` or `files` (critic C-14); `pnpm release:pack`
  names it more precisely;
* `Unsupported URL Type "workspace:"` → the tarball was packed with npm instead of pnpm;
* "No brand table" in the browser → the app did not hand its brand to `<Theme tokens={…}>` or
  `setBrandTokens()` (ADR-0020 §6);
* a Swift compile error → the package's public API changed under a consumer.
