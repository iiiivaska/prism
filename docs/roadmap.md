# Roadmap

Implementation plan for Prism after the blueprint. Each ticket is self-contained for `/execute-ticket`: it names its inputs, its acceptance check and the ADR it serves. Tickets inside a phase may run in parallel unless a dependency is listed. The system version stays `0.1.0` until Phase 3 ships the vertical slice; `0.2.0` closes Phase 5.

- **SwiftUI `Gradient.ColorSpace.perceptual` is OKLab** (ARCHITECTURE V14): verified 2026-09-16 on macOS 26 and the iOS 26.5 and watchOS 26.5 simulators, and the fallback is the one that ships. `.perceptual` *is* OKLab — a two-stop gradient rendered with `ImageRenderer` sits 0.7/255 from the OKLab samples while gamma-encoded sRGB is 5/255 and linear light 37/255 away, and `.device` is gamma-encoded sRGB to 0.3/255 — but an 8-bit render of the seeded gradients drifts up to 2.4/255 from those samples, above the 1/255 the P3-1 acceptance asks for. DSCore therefore takes the documented fallback: `DSGradient.stops` resamples each authored segment in OKLab (sixteen interior stops, kept in the stops' own color space) and draws them with `.device`, which measures within 1/255 on all three platforms. Held by `DSGradientTests` (`perceptualIsOKLab`, `deviceIsGammaEncodedSRGB`, `everySeededGradientInterpolatesInOKLab`). One divergence stays and is counted, not asserted away: the OKLab path between two dark saturated stops leaves the sRGB gamut, where an sRGB render clips and CSS gamut-maps (ARCHITECTURE §7.2) (P3-1).

- **SwiftUI blur radius against CSS `blur()`** (ADR-0030 §4.3): verified 2026-09-16 on macOS 26 and the iOS 26.5 and watchOS 26.5 simulators, and it does not. `.blur(radius: r)` renders a Gaussian of standard deviation ≈ 0.90 × r, measured on a step edge three ways (the second moment of the step's derivative and the 10 %/90 % and 25 %/75 % crossings) at radii from 8 to 75. DSCore therefore scales the token value: every blur token is the CSS standard deviation, and `DSBlur.radius(cssStandardDeviation:)` divides by 0.90 (`DSGlassRecipe.blurRadius` is what a Surface passes to SwiftUI, and the vivid bloom's 75 goes the same way). Held by `DSBlurTests` (P3-1).

- **Button `primary` has no Reduce Motion press** (ADR-0023 §8.4, `Button.yaml` `accessibility.reduceMotion`): **open, and shipped that way.** The substitute the spec names, `comp.button.primary.bg.pressed`, aliases `color.bg.fill.inverse` — which is also `comp.button.primary.bg.rest`, and on vivid both cells are forced to `color.bg.fill.inverse-media` — so the pressed pill is pixel-identical to the pill at rest, on both grounds and in both schemes, while `secondary`, `ghost` and `danger` move 10 to 15 code values there. The component cannot repair it: `color.bg.fill.neutral.subtle`, the substitute `danger` and Card take, is the inverse fill's own colour at 6 % and composites to nothing over it (`DSButtonAppearance.reducedMotionPressOverlay`). The fix is a token — give `comp.button.primary.bg.pressed` a value distinct from `comp.button.primary.bg.rest`, and the `-media` pair on vivid, through P1-1 and P1-2 — and it is a token both stacks read, so neither implementation changes with it. `DSButtonReduceMotionTests.theReduceMotionPressIsVisible` records it as a known issue for `primary` alone and fails the day the token lands, which is when the wrapper comes off (P1-1, P1-2).
